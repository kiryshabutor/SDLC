## 1. Введение {#1-introduction}

Документ содержит спецификацию требований к веб-сервису «Охотник за скидками в Steam» — сервису, который отслеживает цены на игры из списка желаемого пользователя, хранит историю цен и уведомляет о скидках. Ниже описаны назначение документа и границы продукта (1.1–1.2), используемые термины (1.3), источники (1.4) и структура документа (1.5).

### 1.1 Назначение документа {#11-document-purpose}

Документ определяет, **что** должна делать система «Охотник за скидками в Steam» версии 1.0 (MVP), но не то, **как** она будет устроена: архитектурные решения описываются в SDD и ADR, которые будут разработаны на последующих этапах курса.

Аудитории документа:

- **Заказчик** (Воронцов И. С.) и **преподаватель** — согласование состава и приоритетов требований, приёмка результата;
- **разработчик** (Бутор К. П.) — проектирование (SDD, ADR) и реализация;
- **тестирование** — разработка тест-кейсов по матрице верификации (раздел 4).

Документ является «живым»: он хранится в Git-репозитории и обновляется через pull request по процедуре из раздела 3.5.10.

### 1.2 Область применения продукта {#12-product-scope}

**Продукт:** веб-сервис «Охотник за скидками в Steam» (далее — Система), релиз R1 (MVP).

**Назначение.** Игроки, ожидающие скидок на конкретные игры, вынуждены вручную проверять страницы магазина Steam, а сам Steam не показывает историю цен и не позволяет задать собственные условия уведомления. Для региона Беларусь история цен Steam не доступна ни в одном из найденных публичных сервисов (см. Приложение В). Система автоматически отслеживает цены игр из вишлиста пользователя в выбранном им регионе Steam, накапливает историю цен и отправляет уведомление, когда выполняется заданное пользователем условие (любая скидка, скидка от N %, цена ниже X, исторический минимум).

**Бизнес-цели:**

| ID | Бизнес-цель | Показатель успеха |
|----|-------------|-------------------|
| BG-1 | Пользователь экономит, покупая игры по лучшей цене | Пользователь узнаёт о каждой скидке, удовлетворяющей его условию, без ручной проверки |
| BG-2 | Пользователь не пропускает распродажи | Уведомление приходит не позже чем через период опроса + 15 минут после изменения цены в Steam (REQ-PERF-005) |
| BG-3 | Пользователь принимает обоснованное решение «покупать сейчас или ждать» | Для каждой игры доступны график цены и исторический минимум с указанием источника данных |
| BG-4 | Сервис может быть развит в коммерческий продукт | Архитектура допускает добавление премиум-функций и партнёрских ссылок без переработки ядра (релиз R2+) |

**Входит в R1:**

- регистрация по email и паролю, подтверждение email, восстановление пароля;
- выбор региона магазина Steam из списка поддерживаемых;
- поиск игр Steam по названию и добавление по ссылке или идентификатору;
- импорт вишлиста из профиля Steam;
- вишлист с условием уведомления для каждой игры;
- периодический сбор цен и хранение истории цен по паре (игра, регион);
- заполнение истории цен задним числом из IsThereAnyDeal для поддерживаемых им регионов;
- страница игры с графиком цены и историческим минимумом;
- уведомления на email, в Telegram и в центре уведомлений на сайте;
- тестовый режим с имитацией цен для демонстрации.

**Не входит в R1:**

- покупка игр и любые платежи внутри Системы;
- магазины, отличные от Steam (GOG, Epic Games Store и т. п.), сравнение цен между магазинами;
- вход через аккаунт Steam (Steam OpenID) — отложено до R2;
- push-уведомления, мобильное приложение;
- премиум-подписка и партнёрские ссылки (BG-4) — отложено до R2+;
- конвертация цен между валютами;
- составные условия уведомления (несколько условий для одной игры) — отложено до R2;
- интерфейс на английском языке — отложено до R2.

## 2. Обзор продукта {#2-product-overview}

### 2.1 Перспектива продукта {#21-product-perspective}

Система — новый самостоятельный продукт, разрабатываемый в рамках курса «Жизненный цикл разработки программного обеспечения». Она не является частью более крупной системы, но зависит от внешних сервисов:

- **магазин Steam** (Valve Corporation) — источник актуальных цен, сведений об играх и вишлистов пользователей;
- **IsThereAnyDeal** — источник прошлой истории цен для поддерживаемых им регионов;
- **почтовый сервер (SMTP)** — доставка писем пользователям.

Система не изменяет данные во внешних сервисах и только читает их. Владелец продукта — Заказчик (Воронцов И. С.); разработка и сопровождение — Бутор К. П. SLA в R1 не заключается, целевые показатели доступности приведены в 3.3.4.

Контекстная диаграмма: [images/context.png](images/context.png) (Приложение А).

```
[Пользователь] ── браузер ──► [Система «Охотник за скидками в Steam»]
                                 │  ├──► Steam Store API / Steam Web API (цены, поиск, вишлист)
                                 │  ├──► IsThereAnyDeal API (история цен)
                                 │  └──► SMTP-сервер ──► почтовый ящик пользователя
```

### 2.2 Функции продукта {#22-product-functions}

1. **Учётная запись:** регистрация по email и паролю, подтверждение email, вход и выход, восстановление пароля, выбор региона, удаление аккаунта.
2. **Поиск игр:** поиск по названию в магазине Steam и добавление по ссылке на страницу игры или по appid.
3. **Импорт вишлиста Steam** по ссылке на профиль.
4. **Вишлист:** просмотр, сортировка, фильтрация, удаление игр, настройка условия уведомления для каждой игры.
5. **Отслеживание цен:** периодический сбор цен в регионах пользователей, хранение истории, ручной запуск проверки.
6. **Аналитика:** страница игры с текущей и обычной ценой, графиком цены и историческим минимумом.
7. **Уведомления:** проверка условий после каждого цикла опроса, email-дайджест, сообщения в Telegram, центр уведомлений на сайте.
8. **Тестовый режим:** имитация изменения цен для демонстрации работы без ожидания реальных распродаж.

Диаграмма вариантов использования: [images/use-cases.png](images/use-cases.png) (Приложение А).

### 2.4 Характеристики пользователей {#24-user-characteristics}

| Класс пользователя | Описание | Уровень подготовки | Частота использования | Доступ |

| Пользователь | Зарегистрированный игрок Steam, ожидающий скидок | Знаком с магазином Steam, понимает понятия «вишлист», «скидка», «регион» | 1–3 раза в неделю; основная работа через email-уведомления | Собственные данные: профиль, вишлист, уведомления |

**Персоны:**

- **Студент-геймер** с ограниченным бюджетом, 10–30 игр в вишлисте Steam, регион BY. Покупает игры только со скидкой и хочет знать, выгодна ли текущая скидка по сравнению с прошлыми распродажами.
- **Коллекционер** с вишлистом 100+ игр. Не готов вручную проверять цены, нуждается в импорте вишлиста и сводных email-уведомлениях вместо десятков отдельных писем.

**Локализация и доступность:** интерфейс R1 — на русском языке; цены отображаются в валюте выбранного региона в том виде, в котором их возвращает Steam. Требования к доступности — REQ-INT-005.

Для сбора цен следует использовать пакетный запрос нескольких appid с фильтром `price_overview`.
- **Rationale:** Steam — единственный источник актуальных цен во всех регионах, включая BY (C-6, A-1).
- **Acceptance Criteria:** Для appid 1245620 в регионах BY и US Система получает цену, совпадающую с ценой на странице магазина Steam в этом регионе; для игры, недоступной в регионе (`success: false`), Система фиксирует признак недоступности.

- **Rationale:** Наблюдаемый лимит Steam — около 200 запросов за 5 минут (A-2); запас снижает риск блокировки IP-адреса сервера.
- **Acceptance Criteria:** В нагрузочном тесте с 2000 отслеживаемых пар число запросов к Steam в любом 5-минутном окне не превышает 150; при имитации ответа 429 следующий запрос отправляется не ранее чем через 60 секунд.
- **Verification Method:** Test

- **Rationale:** Поддержка импорта вишлиста (REQ-FUNC-010) по обоим форматам ссылок на профиль.
- **Acceptance Criteria:** Для публичного профиля импортируются все appid из вишлиста Steam; vanity URL корректно преобразуется в SteamID64.
- **Verification Method:** Test
- **More Information:** Старый эндпоинт `store.steampowered.com/wishlist/profiles/<id>/wishlistdata/` не работает (HTTP 302) и не должен использоваться.

- **ID:** REQ-INT-009
- **Title:** IsThereAnyDeal API
- **Statement:** Система должна использовать IsThereAnyDeal API (ключ передаётся в заголовке `ITAD-API-Key`): `GET /games/lookup/v1` — для сопоставления appid с идентификатором ITAD, `GET /games/history/v2` с фильтром магазина Steam (`shops=61`) — для получения истории цен, `POST /games/storelow/v2` с фильтром `shops=61` — для получения исторического минимума в Steam.
- **Rationale:** Заполнение истории цен задним числом (REQ-FUNC-019) и мировая история скидок (REQ-FUNC-024).
- **Acceptance Criteria:** Для Elden Ring (appid 1245620) в регионе US Система получает историю цен Steam не менее чем за 12 месяцев и исторический минимум $35.99.
- **Verification Method:** Test
- **More Information:** Лимит ITAD — 1000 запросов за 5 минут; при ответе 429 Система должна выдерживать паузу из заголовка `Retry-After`.

### 3.2 Функциональные требования {#32-functional}

#### 3.2.1 Учётная запись {#321-account}

- **ID:** REQ-FUNC-001
- **Title:** Регистрация
- **Statement:** Система должна позволять гостю зарегистрироваться, указав email, пароль, повтор пароля и регион из списка поддерживаемых (REQ-FUNC-005), а также подтвердив согласие на обработку персональных данных. Пароль должен содержать не менее 8 символов, в том числе хотя бы одну букву и одну цифру.
- **Rationale:** Учётная запись нужна для хранения вишлиста; email служит каналом уведомлений.
- **Acceptance Criteria:** При корректных данных создаётся учётная запись и отправляется письмо подтверждения (REQ-FUNC-002). При некорректном формате email, коротком или несовпадающем пароле, отсутствии согласия или занятом email регистрация отклоняется с сообщением у соответствующего поля.
- **Verification Method:** Test
- **More Information:** Источник — интервью с Заказчиком. Связано с REQ-SEC-001, REQ-COMP-001.

- **ID:** REQ-FUNC-002
- **Title:** Подтверждение email
- **Statement:** Система должна отправлять на указанный при регистрации email письмо со ссылкой подтверждения, действительной 24 часа. До подтверждения email-уведомления о ценах не отправляются, а в интерфейсе отображается баннер с кнопкой повторной отправки письма (не чаще одного раза в 60 секунд).
- **Rationale:** Уведомления не должны уходить на опечатанный или чужой адрес.
- **Acceptance Criteria:** Переход по ссылке в течение 24 часов подтверждает email; по истечении срока или при повторном использовании ссылки выводится сообщение о недействительности и предложение отправить письмо заново.
- **Verification Method:** Test
- **More Information:** Связано с REQ-SEC-006.

- **ID:** REQ-FUNC-003
- **Title:** Вход и выход
- **Statement:** Система должна позволять пользователю войти по email и паролю и выйти из учётной записи. При неверной паре email/пароль Система должна выводить единое сообщение «Неверный email или пароль», не уточняя, какое из полей неверно.
- **Rationale:** Доступ к личным данным; защита от определения зарегистрированных адресов.
- **Acceptance Criteria:** Корректные данные открывают экран вишлиста; после выхода защищённые страницы недоступны без повторного входа.
- **Verification Method:** Test
- **More Information:** Связано с REQ-SEC-003, REQ-SEC-005.

- **ID:** REQ-FUNC-004
- **Title:** Восстановление пароля
- **Statement:** Система должна позволять пользователю запросить по email ссылку для сброса пароля, действительную 1 час и пригодную для однократного использования, и задать по ней новый пароль. После сброса все активные сессии пользователя должны завершаться.
- **Rationale:** Пользователь не должен терять доступ к накопленному вишлисту из-за забытого пароля.
- **Acceptance Criteria:** Ссылка позволяет задать новый пароль один раз в течение часа; старый пароль после этого не действует; ответ на запрос сброса одинаков для существующего и несуществующего email (REQ-SEC-007).
- **Verification Method:** Test

- **ID:** REQ-FUNC-005
- **Title:** Выбор региона

Цены, история цен и условия уведомлений пользователя должны отображаться и проверяться для выбранного региона. - **More Information:** Список регионов задаётся конфигурацией; состав BY, RU, KZ, US, PL подтверждён Заказчиком 10.10.2026 (Приложение Д). Признак поддержки ITAD в R1: US, PL — да; BY, RU, KZ — нет.

- **Acceptance Criteria:** При отключённых email-уведомлениях после срабатывания условия письмо не отправляется, а уведомление появляется на сайте; при включённых обоих каналах пользователь получает и письмо, и сообщение в Telegram.

- **More Information:** Версия 1 требования (частота «раз в сутки») **отменена** по решению Заказчика 31.10.2026 (PR #2, второй раунд), в том числе для R2.

#### 3.2.3 Вишлист {#323-wishlist}

- **ID:** REQ-FUNC-012
- **Title:** Просмотр вишлиста

- **Title:** Сортировка и фильтрация вишлиста
- **Statement:** Система должна позволять сортировать вишлист по названию, текущей цене, проценту скидки и дате добавления, а также фильтровать по признакам «только со скидкой» и «только на историческом минимуме».
- **Rationale:** Для вишлистов из десятков и сотен игр (персона «Коллекционер»).
- **Acceptance Criteria:** Каждый вариант сортировки и фильтра даёт ожидаемый порядок и состав списка на тестовом наборе из 20 игр.
- **Verification Method:** Test

- **ID:** REQ-FUNC-014
- **Title:** Удаление игры из вишлиста
- **Statement:** Система должна позволять удалить игру из вишлиста; после удаления по игре не создаются уведомления для этого пользователя.
- **Rationale:** Пользователь купил игру или потерял к ней интерес.
- **Acceptance Criteria:** Удалённая игра отсутствует в вишлисте; при последующем изменении её цены уведомление пользователю не создаётся.
- **Verification Method:** Test

- **ID:** REQ-FUNC-015
- **Title:** Условие уведомления
- **Statement:** Система должна позволять для каждой игры вишлиста задать ровно одно условие уведомления из списка: (а) любая скидка — процент скидки больше 0; (б) скидка не менее N % — N целое от 1 до 99; (в) цена ниже X — X положительное число в валюте региона пользователя, условие выполняется при итоговой цене ≤ X; (г) исторический минимум — итоговая цена со скидкой не больше исторического минимума (REQ-FUNC-023). Условие по умолчанию — «любая скидка».
- **Rationale:** Разные пользователи считают выгодными разные скидки; ключевая отличительная функция продукта (BG-1).
- **Acceptance Criteria:** Для каждого типа условия проверены значения на границе (например, для «скидка не менее 30 %»: скидка 29 % — не выполнено, 30 % — выполнено); недопустимые значения N и X отклоняются с сообщением.

- **More Information:** Проверка условий — REQ-FUNC-025.

- **ID:** REQ-FUNC-016
- **Title:** Особые состояния игр

Для таких игр условия уведомления не проверяются до изменения состояния.

- **Acceptance Criteria:** Cyberpunk 2077 (appid 1091500) в регионе BY отображается с пометкой «Недоступна в вашем регионе»; при смене региона на US отображается её цена.
- **Verification Method:** Test

#### 3.2.4 Отслеживание цен {#324-price-tracking}

- **ID:** REQ-FUNC-017
- **Title:** Периодический сбор цен
- **Statement:** Система должна с периодом, задаваемым конфигурацией (по умолчанию 3 часа, допустимо от 1 до 24 часов), выполнять цикл опроса: получать из Steam текущую цену, обычную цену и процент скидки для каждой уникальной пары (игра, регион), присутствующей хотя бы в одном вишлисте. Каждая пара запрашивается не более одного раза за цикл независимо от числа пользователей, отслеживающих игру.
- **Rationale:** Ядро продукта; опрос по уникальным парам минимизирует число запросов к Steam (REQ-INT-007).
- **Acceptance Criteria:** Если игру отслеживают 3 пользователя в регионе BY и 1 в регионе US, за цикл выполняется ровно 2 запроса цены этой игры (по одному на регион, с учётом пакетирования); цикл запускается автоматически по расписанию.
- **Verification Method:** Test

- **ID:** REQ-FUNC-018
- **Title:** Хранение истории цен
- **Statement:** Система должна сохранять запись истории (игра, регион, итоговая цена, обычная цена, процент скидки, валюта, время, источник) при первом получении цены пары и при каждом изменении итоговой цены или процента скидки. Время последней успешной проверки пары должно храниться отдельно. Записи истории должны храниться не менее 2 лет.
- **Rationale:** Собственная история — единственный источник истории цен для регионов BY, RU, KZ (A-5); запись только изменений сокращает объём данных.
- **Acceptance Criteria:** При трёх циклах с неизменной ценой создаётся одна запись истории, а время последней проверки обновляется трижды; при изменении цены создаётся новая запись.
- **Verification Method:** Test

- **ID:** REQ-FUNC-019
- **Title:** Заполнение истории из ITAD
- **Statement:** При первом добавлении игры в вишлист для региона, поддерживаемого ITAD (US, PL), Система должна загрузить из ITAD историю цен этой игры в магазине Steam не менее чем за 2 года и сохранить её с источником «ITAD». Для регионов, не поддерживаемых ITAD, данные ITAD не должны записываться в историю цен региона.
- **Rationale:** Без прошлой истории график и условие «исторический минимум» бесполезны в первые недели (BG-3); ITAD для BY, RU, KZ возвращает данные США, которые исказили бы историю (A-5).
- **Acceptance Criteria:** После добавления Elden Ring пользователем региона US на графике присутствуют распродажи 2025 года; для пользователя региона BY история региона BY содержит только записи с источником «Steam».
- **Verification Method:** Test
- **More Information:** Связано с REQ-INT-009, REQ-REL-004. В первом раунде обсуждения перенесено в R2, во втором раунде возвращено в R1 по решению Заказчика (PR #2, 31.10.2026): без истории ITAD график для US и PL пуст в первые месяцы.

- **ID:** REQ-FUNC-020
- **Title:** Ручная проверка цен
- **Statement:** Система должна позволять пользователю запустить внеочередную проверку цен игр своего вишлиста кнопкой «Проверить цены сейчас» не чаще одного раза в 10 минут; после проверки обновлённые цены и созданные уведомления отображаются без перезагрузки страницы.
- **Rationale:** Демонстрация работы Системы и проверка цены в начале распродажи без ожидания очередного цикла.
- **Acceptance Criteria:** Нажатие запускает проверку, кнопка блокируется на 10 минут с отображением оставшегося времени; результат проверки отражается в вишлисте.
- **Verification Method:** Demonstration

#### 3.2.5 Страница игры и аналитика {#325-game-page}

- **ID:** REQ-FUNC-021
- **Title:** Страница игры
- **Statement:** Система должна отображать страницу игры с обложкой, названием, текущей и обычной ценой, процентом скидки, историческим минимумом с датой и источником, условием уведомления с возможностью его изменить, графиком истории цен и ссылкой на страницу игры в магазине Steam.

- **Title:** График истории цен

На графике должны быть отмечены точка исторического минимума и линия обычной цены, а участки, полученные из ITAD, — визуально отличаться от собственных данных и сопровождаться подписью источника.

- **Statement:** Система должна вычислять исторический минимум игры в регионе как наименьшую итоговую цену в магазине Steam среди всех записей истории этого региона (собственных и, для поддерживаемых ITAD регионов, загруженных из ITAD). Если история региона охватывает менее 90 дней, рядом с минимумом должна отображаться пометка «История неполная: данные с <дата>».

- **ID:** REQ-FUNC-024
- **Title:** Мировая история скидок

#### 3.2.6 Уведомления {#326-notifications}

- **ID:** REQ-FUNC-025
- **Title:** Проверка условий уведомлений
- **Statement:** После получения цены пары (игра, регион) в цикле опроса или при ручной проверке Система должна проверить условия уведомления всех пользователей этого региона, отслеживающих игру, и создать уведомление для каждого пользователя, условие которого выполнено.
- **Rationale:** Основная ценность продукта — пользователь не проверяет цены сам (BG-1, BG-2).
- **Acceptance Criteria:** При снижении цены Elden Ring в регионе BY с $39.99 до $23.99 (−40 %) уведомление создаётся для пользователей региона BY с условиями «любая скидка», «скидка не менее 40 %», «цена ниже 25» и не создаётся для пользователей с условием «скидка не менее 50 %» и для пользователей других регионов.
- **Verification Method:** Test

- **ID:** REQ-FUNC-026
- **Title:** Защита от повторных уведомлений
- **Statement:** Система не должна создавать повторное уведомление пользователю по той же игре, пока итоговая цена не изменится. После окончания скидки и последующего нового выполнения условия уведомление создаётся снова.
- **Rationale:** Без этого при периоде опроса 3 часа пользователь получал бы одно и то же уведомление 8 раз в сутки на протяжении всей распродажи.
- **Acceptance Criteria:** При неизменной цене со скидкой в течение 5 циклов создаётся одно уведомление; при дополнительном снижении цены — ещё одно; после окончания скидки и новой распродажи — ещё одно.
- **Verification Method:** Test

- **ID:** REQ-FUNC-027-2
- **Title:** Email-уведомление
- **Statement:** Система должна отправлять пользователю с подтверждённым email и включёнными email-уведомлениями (REQ-FUNC-006-2) не более одного письма-дайджеста за цикл опроса со всеми уведомлениями цикла. Для каждой игры в письме указываются название, итоговая и обычная цена, процент скидки, отметка «исторический минимум» при её наличии и ссылка на страницу игры в Steam. Письмо должно содержать ссылку отписки от email-уведомлений (REQ-FUNC-029).
- **Rationale:** Сводное письмо вместо десятков отдельных писем во время крупных распродаж (персона «Коллекционер»).
- **Acceptance Criteria:** При срабатывании условий по 5 играм за один цикл пользователь получает одно письмо с 5 позициями; пример строки: «Elden Ring: −40 %, $23.99 (было $39.99) — исторический минимум!».
- **Verification Method:** Test
- **More Information:** Режим «раз в сутки» из версии 1 требования **отменён** (PR #2, 31.10.2026).

- **ID:** REQ-FUNC-028
- **Title:** Центр уведомлений на сайте
- **Statement:** Система должна отображать список уведомлений пользователя (новые сверху) с датой, игрой, ценой и скидкой, выделять непрочитанные, показывать их число в панели навигации и позволять отметить все уведомления прочитанными. Уведомления хранятся 90 дней.
- **Rationale:** Резервный канал на случай недоставки письма (A-7) и для пользователей с отключёнными email-уведомлениями.
- **Acceptance Criteria:** Новое уведомление появляется в центре уведомлений после цикла опроса независимо от отправки email; после «Отметить все прочитанными» счётчик равен 0.
- **Verification Method:** Test

- **ID:** REQ-FUNC-029
- **Title:** Отписка из письма
- **Statement:** Система должна отключать email-уведомления пользователя по переходу по ссылке отписки из письма без ввода пароля и показывать страницу с подтверждением и возможностью снова включить уведомления.
- **Rationale:** Удобство пользователя; общепринятая практика для рассылок.
- **Acceptance Criteria:** После перехода по ссылке настройка email-уведомлений пользователя выключена; ссылка не позволяет изменить никакие другие данные.
- **Verification Method:** Test

- **ID:** REQ-FUNC-031
- **Title:** Уведомления в Telegram
- **Statement:** Система должна позволять пользователю привязать аккаунт Telegram: по кнопке «Подключить Telegram» в профиле Система выдаёт одноразовый код (действует 15 минут) и ссылку на бота; после отправки кода боту аккаунт привязывается. Привязанному пользователю с включённым каналом Telegram Система должна отправлять после каждого цикла опроса одно сообщение со всеми уведомлениями цикла в том же формате, что и письмо (REQ-FUNC-027-2). Пользователь должен иметь возможность отвязать Telegram в профиле или командой боту `/stop`.
- **Rationale:** Письма многие пользователи читают с опозданием, а сообщения в Telegram просматривают сразу; без этого канала Заказчик считает сервис неконкурентоспособным (PR #2, второй раунд).
- **Acceptance Criteria:** После привязки и срабатывания условия по 3 играм за цикл пользователь получает в Telegram одно сообщение с 3 позициями не позднее чем через 1 минуту после завершения цикла; после `/stop` сообщения не отправляются; просроченный или повторно использованный код отклоняется.
- **Verification Method:** Test
- **More Information:** Добавлено 31.10.2026 по запросу Заказчика, приоритет 20, релиз R1. Связано с REQ-INT-012.

#### 3.2.7 Тестовый режим {#327-test-mode}

- **ID:** REQ-FUNC-030
- **Title:** Тестовый источник цен
- **Statement:** Система должна поддерживать тестовый режим, включаемый конфигурацией и недоступный при выключенной настройке, в котором вместо Steam используется имитированный источник цен. В тестовом режиме разработчик должен иметь возможность вручную задать цену и скидку для пары (игра, регион) и немедленно запустить цикл опроса.
- **Rationale:** Демонстрация полного сценария (изменение цены → запись в истории → уведомление → график) на защите без ожидания реальной распродажи Steam.
- **Acceptance Criteria:** В тестовом режиме установка скидки 50 % для игры из вишлиста приводит к появлению записи истории, уведомлению на сайте и email-дайджесту в течение 1 минуты; при выключенном тестовом режиме функции имитации недоступны (HTTP 404).
- **Verification Method:** Demonstration

### 3.3 Качество обслуживания {#33-quality-of-service}

Целевые показатели приведены для эталонного окружения: один сервер с 2 vCPU и 4 ГБ ОЗУ, 1000 пользователей, 2000 отслеживаемых пар (игра, регион) (A-9).

#### 3.3.1 Производительность {#331-performance}

- **ID:** REQ-PERF-001
- **Title:** Время отклика API
- **Statement:** API-сервер должен отвечать на запросы, не требующие обращения к внешним сервисам (вишлист, страница игры, уведомления), за время не более 300 мс для 95 % запросов при 50 одновременных пользователях.
- **Rationale:** Комфортная работа с интерфейсом.
- **Acceptance Criteria:** Нагрузочный тест (50 виртуальных пользователей, 10 минут) показывает p95 ≤ 300 мс.
- **Verification Method:** Test

- **ID:** REQ-PERF-002
- **Title:** Время поиска
- **Statement:** Поиск игр по названию (REQ-FUNC-008) должен возвращать результат не более чем за 3 секунды для 95 % запросов при доступном Steam.
- **Rationale:** Поиск зависит от внешнего Steam API, поэтому порог выше, чем для внутренних запросов.
- **Acceptance Criteria:** Серия из 100 поисковых запросов показывает p95 ≤ 3 с.
- **Verification Method:** Test

- **ID:** REQ-PERF-003
- **Title:** Загрузка интерфейса
- **Statement:** Первичная загрузка веб-клиента до появления интерактивного экрана вишлиста должна занимать не более 3 секунд при соединении 10 Мбит/с.
- **Rationale:** Пользователь переходит по ссылке из письма и ожидает быстрого открытия.
- **Acceptance Criteria:** Метрика Time to Interactive в Lighthouse с профилем сети 10 Мбит/с ≤ 3 с.
- **Verification Method:** Test

- **ID:** REQ-PERF-004
- **Title:** Длительность цикла опроса
- **Statement:** Цикл опроса 2000 пар (игра, регион) должен завершаться не более чем за 60 минут с соблюдением REQ-INT-007.
- **Rationale:** Цикл должен укладываться в минимальный допустимый период опроса (1 час, REQ-FUNC-017).
- **Acceptance Criteria:** В тесте с имитацией Steam с задержкой ответа 500 мс и 2000 парами цикл завершается за ≤ 60 минут.
- **Verification Method:** Test

- **ID:** REQ-PERF-005
- **Title:** Задержка уведомления
- **Statement:** Уведомление должно создаваться не позднее чем через период опроса плюс 15 минут после изменения цены в Steam.
- **Rationale:** Пользователь не должен пропускать короткие распродажи (BG-2).
- **Acceptance Criteria:** В тестовом режиме (REQ-FUNC-030) время от изменения цены до появления уведомления не превышает установленного периода плюс 15 минут.
- **Verification Method:** Test

- **ID:** REQ-PERF-006
- **Title:** Объём хранилища
- **Statement:** Объём базы данных при 1000 пользователях, 2000 парах и истории за 2 года не должен превышать 1 ГБ.
- **Rationale:** Учебная эксплуатация на сервере с ограниченными ресурсами (REQ-COST-001).
- **Acceptance Criteria:** Расчёт по словарю данных (Приложение Б) и проверка на сгенерированном наборе данных дают объём ≤ 1 ГБ.
- **Verification Method:** Analysis

#### 3.3.2 Безопасность {#332-security}

- **ID:** REQ-SEC-001
- **Title:** Хранение паролей
- **Statement:** Система должна хранить пароли только в виде хэша, вычисленного алгоритмом Argon2id или bcrypt (cost ≥ 12) с уникальной солью.
- **Rationale:** Защита паролей при компрометации базы данных.
- **Acceptance Criteria:** В БД отсутствуют пароли в открытом виде; формат хэша соответствует указанному алгоритму.
- **Verification Method:** Inspection

- **ID:** REQ-SEC-002
- **Title:** Шифрование при передаче
- **Statement:** В рабочем окружении весь обмен между браузером и Системой должен выполняться по HTTPS (TLS 1.2 и выше); запросы по HTTP должны перенаправляться на HTTPS.
- **Rationale:** Защита учётных данных и сессий при передаче.
- **Acceptance Criteria:** Запрос по HTTP получает перенаправление 301 на HTTPS; соединение с TLS 1.0/1.1 отклоняется.
- **Verification Method:** Test

- **ID:** REQ-SEC-003
- **Title:** Управление сессиями
- **Statement:** Идентификатор сессии должен передаваться в cookie с атрибутами `HttpOnly`, `Secure` и `SameSite=Lax`; сессия должна завершаться через 30 дней неактивности, при выходе и при сбросе пароля.
- **Rationale:** Защита от кражи сессии через XSS и от CSRF.
- **Acceptance Criteria:** Атрибуты cookie подтверждены инспекцией; после выхода прежний идентификатор сессии не принимается сервером.
- **Verification Method:** Test

- **ID:** REQ-SEC-004
- **Title:** Авторизация доступа к данным
- **Statement:** Пользователь должен иметь доступ только к собственным вишлисту, уведомлениям и настройкам; запросы к чужим данным должны отклоняться ответом HTTP 404.
- **Rationale:** Конфиденциальность данных пользователей.
- **Acceptance Criteria:** Автотест: пользователь A, подставляя идентификаторы записей пользователя B, не получает и не изменяет данные B.
- **Verification Method:** Test

- **ID:** REQ-SEC-005
- **Title:** Защита от перебора
- **Statement:** После 5 неудачных попыток входа для одного email в течение 15 минут Система должна блокировать вход для этого email на 15 минут; запросы на сброс пароля и повторную отправку письма подтверждения должны ограничиваться 5 запросами в час на email.
- **Rationale:** Защита от подбора паролей и злоупотребления отправкой писем.
- **Acceptance Criteria:** 6-я попытка входа в течение 15 минут отклоняется сообщением о временной блокировке даже при верном пароле.
- **Verification Method:** Test

- **ID:** REQ-SEC-006
- **Title:** Токены подтверждения и сброса
- **Statement:** Токены подтверждения email и сброса пароля должны генерироваться криптографически стойким генератором (не менее 128 бит энтропии), храниться в БД только в виде хэша и становиться недействительными после использования или истечения срока.
- **Rationale:** Невозможность подбора или повторного использования ссылок.
- **Acceptance Criteria:** Инспекция кода и БД; повторное использование токена отклоняется.
- **Verification Method:** Inspection

- **ID:** REQ-SEC-007
- **Title:** Неразглашение зарегистрированных адресов
- **Statement:** Ответы на запрос сброса пароля и на вход с неверными данными не должны позволять определить, зарегистрирован ли email в Системе.
- **Rationale:** Защита от сбора списка пользователей.
- **Acceptance Criteria:** Ответы для существующего и несуществующего email совпадают по тексту и коду ответа.
- **Verification Method:** Test

- **ID:** REQ-SEC-008
- **Title:** Хранение секретов
- **Statement:** Ключи ITAD и Steam Web API, учётные данные SMTP и БД должны передаваться Системе через переменные окружения и не должны храниться в репозитории исходного кода.
- **Rationale:** Предотвращение утечки ключей через публичный репозиторий.
- **Acceptance Criteria:** Сканирование репозитория (например, gitleaks) не находит секретов; репозиторий содержит только `.env.example` без реальных значений.
- **Verification Method:** Inspection

- **ID:** REQ-SEC-009
- **Title:** Защита от типовых атак
- **Statement:** Система должна валидировать все входные данные на сервере, использовать только параметризованные SQL-запросы, экранировать выводимые данные и защищать изменяющие запросы от CSRF.
- **Rationale:** Защита от уязвимостей класса OWASP Top 10 (инъекции, XSS, CSRF).
- **Acceptance Criteria:** Автоматическое сканирование (например, OWASP ZAP baseline) не выявляет уязвимостей высокого уровня; инспекция кода не выявляет конкатенации SQL.
- **Verification Method:** Test

- **ID:** REQ-SEC-010
- **Title:** Минимизация персональных данных
- **Statement:** Система должна хранить о пользователе только email, хэш пароля, регион, настройки уведомлений, ссылку на профиль Steam (если указана) и SteamID64.
- **Rationale:** Принцип минимизации персональных данных (REQ-COMP-001).
- **Acceptance Criteria:** Схема БД не содержит других персональных данных.
- **Verification Method:** Inspection

#### 3.3.3 Надёжность {#333-reliability}

- **ID:** REQ-REL-001
- **Title:** Повторы при ошибках внешних API
- **Statement:** При ошибке сети, таймауте (10 секунд) или ответе HTTP 5xx/429 от Steam или ITAD Система должна повторять запрос до 3 раз с экспоненциальной задержкой (1, 2, 4 секунды), а при наличии заголовка `Retry-After` — с указанной в нём задержкой.
- **Rationale:** Кратковременные сбои внешних сервисов не должны приводить к потере данных цикла.
- **Acceptance Criteria:** При имитации двух подряд ошибок 503 третий запрос успешен, и цена сохраняется.
- **Verification Method:** Test

- **ID:** REQ-REL-002
- **Title:** Изоляция ошибок в цикле опроса
- **Statement:** Ошибка получения цены одной пары не должна прерывать цикл опроса для остальных пар; такая пара должна быть повторно запрошена в следующем цикле.
- **Rationale:** Одна проблемная игра не должна лишать уведомлений всех пользователей.
- **Acceptance Criteria:** При имитации постоянной ошибки для одной пары из 100 остальные 99 обработаны, ошибка записана в журнал.
- **Verification Method:** Test

- **ID:** REQ-REL-003
- **Title:** Деградация при недоступности Steam
- **Statement:** При недоступности Steam Система должна продолжать отображать последние известные цены с указанием времени последней успешной проверки, а поиск — выводить сообщение «Магазин Steam временно недоступен, попробуйте позже».
- **Rationale:** Сохранение работоспособности основных функций при сбое внешнего сервиса.
- **Acceptance Criteria:** При блокировке доступа к Steam вишлист и страницы игр открываются с последними ценами и временем проверки.
- **Verification Method:** Test

- **ID:** REQ-REL-004
- **Title:** Деградация при недоступности ITAD
- **Statement:** При недоступности ITAD или отсутствии ключа Система должна работать только с собственной историей цен; блок мировой истории скидок (REQ-FUNC-024) скрывается, а загрузка истории (REQ-FUNC-019) повторяется при следующем цикле.
- **Rationale:** ITAD — дополнительный источник (A-6) и не должен быть точкой отказа.
- **Acceptance Criteria:** При пустом ключе ITAD все функции, кроме REQ-FUNC-019 и REQ-FUNC-024, работают.
- **Verification Method:** Test

- **ID:** REQ-REL-005
- **Title:** Доставка email
- **Statement:** При ошибке отправки письма Система должна повторить отправку до 3 раз с интервалом 5 минут; уведомления в центре уведомлений должны создаваться независимо от результата отправки.
- **Rationale:** Сбой почтового сервера не должен приводить к потере уведомлений (A-7).
- **Acceptance Criteria:** При имитации недоступности SMTP уведомления появляются на сайте, а письмо отправляется после восстановления SMTP в пределах 3 попыток.
- **Verification Method:** Test

- **ID:** REQ-REL-006
- **Title:** Идемпотентность цикла опроса
- **Statement:** Аварийное завершение и перезапуск фонового обработчика во время цикла не должны приводить к дублированию записей истории цен и уведомлений.
- **Rationale:** Корректность истории и защита от повторных писем.
- **Acceptance Criteria:** Принудительная остановка обработчика в середине цикла и перезапуск не создают дубликатов в таблицах истории и уведомлений.
- **Verification Method:** Test

#### 3.3.4 Доступность {#334-availability}

- **ID:** REQ-AVAIL-001
- **Title:** Целевая доступность
- **Statement:** Веб-интерфейс и API следует обеспечивать доступными не менее 99 % времени в месяц (не более 7,3 часа простоя), не считая плановых работ, о которых пользователи уведомляются баннером не менее чем за 24 часа.
- **Rationale:** Учебная эксплуатация без дежурной смены; показатель реалистичен для одного сервера.
- **Acceptance Criteria:** Внешний мониторинг доступности за месяц показывает ≥ 99 %.
- **Verification Method:** Analysis

- **ID:** REQ-AVAIL-002
- **Title:** Автоматический перезапуск
- **Statement:** Компоненты Системы должны автоматически перезапускаться при аварийном завершении и после перезагрузки сервера; фоновый обработчик после перезапуска должен продолжать работу по расписанию.
- **Rationale:** Восстановление без ручного вмешательства.
- **Acceptance Criteria:** После принудительного завершения процесса API-сервера он снова доступен не более чем через 1 минуту.
- **Verification Method:** Test

- **ID:** REQ-AVAIL-003
- **Title:** Резервное копирование
- **Statement:** База данных должна резервироваться ежедневно с хранением 7 последних копий; допустимая потеря данных (RPO) — 24 часа, время восстановления (RTO) — 2 часа.
- **Rationale:** История цен по регионам BY, RU, KZ невосстановима из внешних источников.
- **Acceptance Criteria:** Восстановление из резервной копии на чистом сервере выполнено за ≤ 2 часа, данные соответствуют моменту копирования.
- **Verification Method:** Demonstration

#### 3.3.5 Наблюдаемость {#335-observability}

- **ID:** REQ-OBS-001
- **Title:** Структурированные журналы
- **Statement:** Компоненты серверной части должны писать журналы в формате JSON со следующими полями: время, уровень, компонент, версия, идентификатор запроса (или цикла), сообщение.
- **Rationale:** Диагностика ошибок и связывание событий одного запроса.
- **Acceptance Criteria:** Каждая строка журнала — корректный JSON с перечисленными полями.
- **Verification Method:** Inspection

- **ID:** REQ-OBS-002
- **Title:** Статистика цикла опроса
- **Statement:** По завершении каждого цикла опроса Система должна записывать в журнал время начала и окончания, число обработанных пар, число ошибок, число запросов к Steam и ITAD, число созданных уведомлений и отправленных писем.
- **Rationale:** Контроль выполнения REQ-PERF-004 и REQ-INT-007.
- **Acceptance Criteria:** После цикла в журнале присутствует запись со всеми перечисленными значениями.
- **Verification Method:** Inspection

- **ID:** REQ-OBS-003
- **Title:** Проверка работоспособности
- **Statement:** API-сервер должен предоставлять эндпоинт `/healthz`, возвращающий HTTP 200 при доступной БД и HTTP 503 при недоступной, а также время окончания последнего успешного цикла опроса.
- **Rationale:** Внешний мониторинг (REQ-AVAIL-001) и автоматический перезапуск.
- **Acceptance Criteria:** При остановленной БД `/healthz` возвращает 503.
- **Verification Method:** Test

- **ID:** REQ-OBS-004
- **Title:** Защита данных в журналах
- **Statement:** Журналы не должны содержать паролей, токенов, ключей API и cookie сессий; email в журналах должен маскироваться (например, `k***@mail.com`).
- **Rationale:** Журналы не должны становиться источником утечки (REQ-COMP-001).
- **Acceptance Criteria:** Поиск по журналам тестового прогона не находит паролей, токенов и полных email-адресов.
- **Verification Method:** Inspection

### 3.4 Соответствие стандартам {#34-compliance}

- **Title:** Защита персональных данных
- **Statement:** Система должна получать согласие пользователя на обработку персональных данных при регистрации, предоставлять доступ к политике обработки персональных данных с каждой страницы и обеспечивать удаление данных по запросу пользователя (REQ-FUNC-007) в соответствии с Законом РБ № 99-З.

- **Title:** Товарные знаки Valve

- **ID:** REQ-COMP-004

### 3.5 Проектирование и реализация {#35-design-and-implementation}

#### 3.5.1 Установка {#351-installation}

- **ID:** REQ-INST-001
- **Title:** Развёртывание одной командой
- **Statement:** Система должна разворачиваться на сервере с установленными Docker и Docker Compose одной командой `docker compose up -d`.
- **Rationale:** Простота развёртывания для демонстрации и проверки преподавателем (C-5).
- **Acceptance Criteria:** На чистом сервере после клонирования репозитория, создания `.env` и выполнения команды Система доступна в браузере не более чем через 5 минут.
- **Verification Method:** Demonstration

- **ID:** REQ-INST-002
- **Title:** Конфигурация через окружение
- **Statement:** Все настраиваемые параметры (адреса, ключи, период опроса, список регионов, тестовый режим, параметры SMTP) должны задаваться переменными окружения; репозиторий должен содержать файл `.env.example` с описанием каждой переменной.
- **Rationale:** Разделение кода и конфигурации; REQ-SEC-008.
- **Acceptance Criteria:** Каждая переменная из `.env.example` описана; при отсутствии обязательной переменной Система завершает запуск с понятным сообщением.
- **Verification Method:** Inspection

- **ID:** REQ-INST-003
- **Title:** Миграции базы данных
- **Statement:** Схема БД должна создаваться и обновляться автоматически при запуске с помощью версионированных миграций; откат последней миграции должен быть возможен.
- **Rationale:** Воспроизводимое развёртывание и обновление без ручных SQL-скриптов.
- **Acceptance Criteria:** Первый запуск на пустой БД создаёт схему; обновление версии применяет новые миграции без потери данных.
- **Verification Method:** Test

#### 3.5.2 Сборка и поставка {#352-build-and-delivery}

- **ID:** REQ-BUILD-001
- **Title:** Воспроизводимая сборка
- **Statement:** Версии зависимостей должны фиксироваться файлами `go.mod`/`go.sum` и `package-lock.json`; сборка образов Docker должна использовать фиксированные версии базовых образов.
- **Rationale:** Одинаковый результат сборки на любой машине.
- **Acceptance Criteria:** Сборка из чистого клона на двух разных машинах завершается успешно с одинаковыми версиями зависимостей.
- **Verification Method:** Inspection

- **ID:** REQ-BUILD-002
- **Title:** Непрерывная интеграция
- **Statement:** Для каждого pull request должны автоматически выполняться статический анализ, модульные тесты и сборка всех компонентов (GitHub Actions); слияние в `main` при неуспешной проверке не допускается.
- **Rationale:** Раннее обнаружение ошибок.
- **Acceptance Criteria:** Pull request с падающим тестом отмечается как непрошедший проверку.
- **Verification Method:** Demonstration

- **ID:** REQ-BUILD-003
- **Title:** Версионирование релизов
- **Statement:** Релизы должны обозначаться по Semantic Versioning (MAJOR.MINOR.PATCH) тегами Git; версия должна отображаться в `/healthz` и журналах.
- **Rationale:** Трассируемость развёрнутой версии.
- **Acceptance Criteria:** Версия в `/healthz` совпадает с тегом Git, из которого выполнена сборка.
- **Verification Method:** Inspection

#### 3.5.3 Распределение {#353-distribution}

- **ID:** REQ-DIST-001
- **Title:** Топология развёртывания
- **Statement:** В R1 все компоненты (веб-клиент, API-сервер, фоновый обработчик, БД) должны размещаться на одном сервере в отдельных контейнерах; одновременно должен выполняться не более чем один цикл опроса.
- **Rationale:** Масштаб R1 (A-9) не требует распределённого развёртывания; параллельные циклы приводили бы к превышению лимитов Steam.
- **Acceptance Criteria:** При запуске второго экземпляра фонового обработчика одновременно выполняется только один цикл.
- **Verification Method:** Test

#### 3.5.4 Сопровождаемость {#354-maintainability}

- **ID:** REQ-MAINT-001
- **Title:** Абстракция источников данных
- **Statement:** Получение цен, поиск игр, импорт вишлиста и получение истории должны выполняться через программные интерфейсы, позволяющие заменить реализацию (Steam, ITAD, тестовый источник) без изменения бизнес-логики.
- **Rationale:** Неофициальный Steam Store API может измениться (A-1); тестовый режим (REQ-FUNC-030).
- **Acceptance Criteria:** Переключение на тестовый источник выполняется только конфигурацией; бизнес-логика не импортирует пакеты конкретных источников.
- **Verification Method:** Inspection

- **ID:** REQ-MAINT-002
- **Title:** Стандарты кодирования
- **Statement:** Код на Go должен проходить `gofmt` и `golangci-lint` без ошибок, код клиентской части — ESLint и Prettier.
- **Rationale:** Единообразие и читаемость кода.
- **Acceptance Criteria:** Проверки в CI (REQ-BUILD-002) проходят без ошибок.
- **Verification Method:** Inspection

- **ID:** REQ-MAINT-003
- **Title:** Покрытие тестами
- **Statement:** Покрытие модульными тестами бизнес-логики (проверка условий уведомлений, вычисление исторического минимума, защита от повторов) должно составлять не менее 70 % строк.
- **Rationale:** Ошибки в этой логике напрямую ведут к ложным или пропущенным уведомлениям.
- **Acceptance Criteria:** Отчёт `go test -cover` для пакетов бизнес-логики показывает ≥ 70 %.
- **Verification Method:** Test

- **ID:** REQ-MAINT-004
- **Title:** Документация
- **Statement:** Репозиторий должен содержать README с инструкцией по запуску, данный SRS, SDD, записи ADR для значимых решений и описание API в формате OpenAPI.
- **Rationale:** Передача проекта и сопровождение; требования курса.
- **Acceptance Criteria:** Перечисленные документы присутствуют и соответствуют текущей версии.
- **Verification Method:** Inspection

#### 3.5.5 Повторное использование {#355-reusability}

- **ID:** REQ-REUSE-001

**Steam Web API — вишлист:** `IWishlistService/GetWishlist/v1?steamid=<SteamID64>` возвращает `{"response":{"items":[{"appid":…,"priority":…,"date_added":…}]}}`; для приватного или пустого вишлиста — `{"response":{}}`.

**IsThereAnyDeal API — сравнение с Steam:**

| | Steam (фактически) | ITAD |
|---|---|---|
| Elden Ring, BY | $39.99 | $59.99 (данные US) |
| Elden Ring, US | $59.99 | $59.99 |
| Elden Ring, PL | 249 zł | 249 zł |
| Cyberpunk 2077, BY | недоступна | $59.99 (данные US) |

История Elden Ring в Steam по данным ITAD (US): −40 % в марте 2025, −40 % в июне 2025, −35 % в декабре 2025, −35 % в марте 2026; исторический минимум в Steam — $35.99 (21.12.2023).

**Альтернативные источники истории цен:** GG.deals — только исторический минимум, бесплатно лишь для личного использования; SteamDB — нет публичного API, регион BY не отслеживается; CheapShark — только цены США. Вывод: история цен для региона BY не доступна ни в одном из найденных сервисов и накапливается Системой самостоятельно.
