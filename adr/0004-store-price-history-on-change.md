# Хранить историю цен только при изменении, текущее состояние отдельно

## Контекст и постановка задачи

Цикл опроса идёт каждые три часа по 2000 парам (игра, регион). Цены в Steam меняются редко: несколько раз в год на распродажах. Если писать запись на каждый опрос, за два года получится около 11,7 млн строк, почти все одинаковые. При этом вишлисту нужно знать время последней проверки, а графику нужны только моменты изменения цены.

Как хранить цены, чтобы история была полной, а объём и время построения графика — малыми?

## Драйверы решения

* Объём БД не более 1 ГБ за два года (REQ-PERF-006).
* История хранится не менее двух лет (REQ-FUNC-018).
* Вишлист показывает время последней проверки каждой игры (REQ-FUNC-012).
* Ступенчатый график строится по точкам изменения (REQ-FUNC-022).
* Повторная обработка той же цены после сбоя не должна создавать дубликат (REQ-REL-006).

## Рассмотренные варианты

* Запись в историю на каждый опрос
* Запись только при изменении + таблица текущего состояния `price_state`
* Агрегаты по дням (одна запись в сутки на пару)

## Итог решения

Выбранный вариант: «Запись только при изменении + таблица текущего состояния», потому что он хранит ровно ту информацию, которая нужна графику, а время проверки обновляется в одной строке `price_state`.

### Последствия

* Хорошо, потому что объём истории около 33 МБ за два года вместо гигабайт (DV-015).
* Хорошо, потому что ступенчатый график строится прямо по записям без обработки.
* Хорошо, потому что `price_state` хранит кэш исторического минимума и вишлист не считает `min()` по истории на каждый запрос.
* Плохо, потому что по истории нельзя сказать, проверялась ли цена в конкретный момент. Для R1 это не требуется, статистика циклов есть в `poll_cycles`.
* Нейтрально, потому что сравнение с предыдущей ценой и вставка выполняются в одной транзакции с блокировкой строки `price_state`.

### Подтверждение

Модульный тест из критерия REQ-FUNC-018: три цикла с неизменной ценой дают одну запись истории и три обновления `checked_at`. Тест идемпотентности: повторная обработка той же цены не меняет число строк.

## Плюсы и минусы вариантов

### Запись на каждый опрос

* Хорошо, потому что простейшая логика.
* Плохо, потому что около 11,7 млн строк за два года и шум на графике.

### Только изменения + `price_state`

* Хорошо, потому что минимальный объём и прямая поддержка графика.
* Нейтрально, потому что две таблицы вместо одной.

### Агрегаты по дням

* Хорошо, потому что предсказуемый объём.
* Плохо, потому что теряются внутридневные изменения: короткая распродажа может не попасть в историю.

## Дополнительная информация

Связанные требования: REQ-FUNC-012, REQ-FUNC-018, REQ-FUNC-022, REQ-FUNC-023, REQ-PERF-006, REQ-REL-006. Элементы SDD: DV-004, DV-007, DV-015.
