# Динамическая модель в UML на PlantUML: правила построения и связи диаграмм

## Контекст и постановка задачи

К началу реализации (итерация 1 плана v3) SDD v0.2 описывал поведение Системы отдельными диаграммами Mermaid (DV-007…DV-011), а SRS содержал диаграмму вариантов использования на SysML v2. Модели прецедентов с потоками событий не было, и поведение, разбросанное по разным представлениям, никак не было связано между собой. Для разработки F-05, F-08 и F-09 нужна единая динамическая модель: что делает каждый актёр (прецеденты), по какому алгоритму (активность), как меняется состояние сущностей (состояния) и какие компоненты обмениваются сообщениями (последовательность).

Как построить динамическую модель, чтобы она оставалась согласованной с SRS, SDD и кодом и обновлялась тем же процессом, что и код (pull request, ревью)?

## Драйверы решения

* Модель хранится в Git рядом с кодом, различия видны в pull request (REQ-CM-001).
* Полная нотация UML 2.5: include, extend, обобщение актёров, дорожки, составные состояния, фрагменты `alt`/`loop`.
* Сборка изображений без платных инструментов и без ручного рисования (REQ-COST-001).
* Прослеживаемость: каждая диаграмма ссылается на прецедент, требования SRS и представление SDD.

## Рассмотренные варианты

* PlantUML: текстовые файлы `.puml` в каталоге `uml/`, PNG собираются скриптом
* Mermaid внутри SDD (как в DV-007…DV-011)
* Графический редактор (draw.io, StarUML) с хранением бинарных файлов

## Итог решения

Выбранный вариант: «PlantUML», потому что он рекомендован методическими указаниями ЛР5, поддерживает все нужные элементы UML (Mermaid не умеет `include`/`extend`, обобщение актёров и дорожки активности), а текстовый формат даёт читаемые различия в pull request.

### Правила построения модели

1. **Идентификаторы.** Прецеденты `UC-NN`, диаграммы активности `AD-NN`, состояний `SM-NN`, последовательности `SD-NN`. Идентификатор пишется в комментарии первой строки `.puml` и в подписи диаграммы в SDD.
2. **Прецеденты.** Имя прецедента начинается с глагола в инфинитиве («Добавить игру в вишлист»). Каждый прецедент даёт актёру законченный результат; шаги одного сценария («Нажать кнопку») прецедентами не являются. Описание по шаблону: краткое описание, актёры, требования, предусловия, основной поток, альтернативные потоки `А*`, потоки ошибок `E*`, постусловия (`docs/use-case-model.md`).
3. **Связи прецедентов.**
   * `include` используется, когда поведение выполняется **всегда** и повторяется в нескольких прецедентах: UC-06, UC-10 и UC-16 включают UC-05 и UC-12. Стрелка идёт от базового прецедента к включаемому.
   * `extend` используется, когда поведение **необязательно** и вставляется в базовый прецедент в точке расширения при условии: UC-03 расширяет UC-02 («забыл пароль»), UC-17 расширяет UC-05 («регион US или PL»). Стрелка идёт от расширяющего прецедента к базовому, а базовый прецедент полон и без расширения.
   * Обобщение используется только для актёров: «Почтовый сервер» и «Telegram» наследуют абстрактного актёра «Канал доставки». Это модельный аналог интерфейса `Notifier` (DV-013): UC-13 работает с любым каналом.
4. **Связи между актёрами не моделируются.** Взаимодействия актёров вне Системы (пользователь пишет боту в Telegram, Steam уведомляет об игре) не влияют на поведение Системы и загромождают диаграмму. Связь прецедента с актёром показывает только обмен с Системой.
5. **Время как актёр.** Плановый цикл не инициирует ни один человек, поэтому для UC-12 введён абстрактный актёр «Время» со стереотипом `<<таймер>>`.
6. **Размер диаграммы и разделение на части.** По СТП 01–2024 надписи на рисунке не мельче 2,5 мм, а все рисунки отчёта одной ширины 12 см. Поэтому все надписи набираются кеглем 16 (заглавная буква 17 px при 150 dpi), а изображение диаграммы не шире 820 px и не выше 17 см на странице. Диаграмма, которая не помещается, делится на части по смыслу, а не механически: модель прецедентов изображена на семи диаграммах по зонам ответственности (`uc-1`…`uc-7`), а диаграммы активности, состояний и последовательности делятся на части с буквами (AD-01a, AD-01b, AD-01c). Часть ссылается на соседнюю вызовом подпроцесса («Обработать пакет (AD-01b)») или подписью «см. SM-01b». Прецедент, нужный на нескольких диаграммах, повторяется с тем же идентификатором. Идентификатор группы без буквы (AD-01) обозначает все её части.
7. **Детализация.** Диаграммы активности и последовательности строятся для прецедентов с нетривиальным алгоритмом или с несколькими участниками (UC-05, UC-12, UC-13). Диаграммы состояний строятся для сущностей, поведение которых зависит от истории событий (элемент вишлиста, запись outbox).
8. **Именование участников.** Дорожки диаграмм активности соответствуют процессам развёртывания (DV-014): «API-сервер», «Фоновый обработчик». Участники диаграмм последовательности соответствуют пакетам кода из DV-003 (`httpapi`, `app`, `domain`, `source`), поэтому диаграмма проверяется чтением кода.
9. **Стиль.** Все диаграммы подключают общий файл `uml/_style.iuml`. Изображения собираются `uml/render.sh` с Graphviz, ручная правка PNG запрещена; узкие высокие изображения скрипт дополняет белыми полями.

### Как связаны диаграммы

```text
SRS REQ-FUNC-…  ──►  UC-NN (поток событий)  ──►  AD-NN (алгоритм прецедента)
                          │                           │
                          ├──► SD-NN (обмен сообщениями между пакетами DV-003)
                          └──► SM-NN (состояния сущностей DV-004, меняемых прецедентом)
                                                      │
                                    SDD DV-016  ◄─────┘   код internal/…
```

* Шаг основного потока прецедента соответствует действию на диаграмме активности; альтернативные потоки и потоки ошибок соответствуют ветвям решений (AD-02a и AD-02b ↔ UC-05, потоки E1…E5).
* Сообщение на диаграмме последовательности соответствует вызову функции или SQL-запросу в коде (SD-01a, SD-01b ↔ `internal/app/wishlist.go`).
* Переход на диаграмме состояний вызывается событием, которое порождает прецедент («цена получена» в UC-12), а действие перехода меняет поле модели данных (`last_notified_price` в DV-004).
* Таблица «Связь прецедентов с другими диаграммами» в `docs/use-case-model.md` и Приложение А SDD фиксируют эти связи для трассировки.

### Последствия

* Хорошо, потому что модель согласована с кодом: при изменении поведения в pull request меняются `.puml`, описание прецедента и код вместе.
* Хорошо, потому что новый разработчик (junior с итерации 3) получает и сценарии, и алгоритмы в одном месте.
* Плохо, потому что для рендера нужны Java и Graphviz; решено скриптом на базе образа `sysml-render`, уже используемого для SysML.
* Нейтрально, потому что диаграммы Mermaid в DV-007…DV-011 сохраняются как краткие эскизы; при расхождении приоритет у UML-модели DV-016.

### Подтверждение

На ревью pull request проверяется: у каждого прецедента на диаграмме есть описание в `docs/use-case-model.md`; каждая диаграмма упомянута в DV-016; `uml/render.sh` выполняется без ошибок, а PNG в `uml/images/` соответствуют исходникам.

## Плюсы и минусы вариантов

### PlantUML

* Хорошо, потому что полная нотация UML, текстовый формат, бесплатный.
* Плохо, потому что автоматическая раскладка Graphviz иногда требует подсказок (длина стрелок, порядок объявления).

### Mermaid в SDD

* Хорошо, потому что GitHub рисует диаграммы прямо в Markdown без сборки.
* Плохо, потому что нет `include`/`extend`, обобщения актёров, дорожек активности; диаграмма прецедентов невозможна.

### Графический редактор

* Хорошо, потому что точный контроль раскладки.
* Плохо, потому что бинарные файлы не сравниваются в pull request и быстро расходятся с кодом.
