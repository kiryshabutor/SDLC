# Развёртывание Docker Compose на одном сервере за Caddy

## Контекст и постановка задачи

По решению Заказчика в PR #1 платный хостинг в R1 не используется, система запускается на компьютере разработчика или на бесплатном сервере (REQ-COST-001). Развернуть её должен уметь и преподаватель одной командой (REQ-INST-001). Нужны HTTPS (REQ-SEC-002), автоматический перезапуск (REQ-AVAIL-002) и ежедневное резервное копирование (REQ-AVAIL-003).

Как упаковать и развернуть систему?

## Драйверы решения

* Запуск одной командой на чистой машине с Docker.
* Стоимость эксплуатации 0 USD.
* HTTPS без ручной работы с сертификатами.
* Автоперезапуск и резервные копии без внешних сервисов.

## Рассмотренные варианты

* Docker Compose на одном сервере, Caddy как обратный прокси
* Docker Compose, nginx и certbot
* Kubernetes (k3s)
* Бинарники и systemd без контейнеров

## Итог решения

Выбранный вариант: «Docker Compose на одном сервере, Caddy», потому что он выполняет все драйверы минимальной конфигурацией: Caddy сам получает и продлевает сертификат, Compose перезапускает контейнеры и описывает всю систему одним файлом.

### Последствия

* Хорошо, потому что `docker compose up -d` поднимает всю систему, а `--profile test` добавляет Mailpit для демонстрации.
* Хорошо, потому что Caddy заменяет nginx и certbot одним контейнером. Для локального запуска он выдаёт самоподписанный сертификат на `localhost`.
* Плохо, потому что один сервер — единая точка отказа. Доступность 99 % (REQ-AVAIL-001) при этом достижима.
* Нейтрально, потому что резервное копирование выполняется отдельным контейнером с `pg_dump` по cron в volume, хранятся семь последних копий.

### Подтверждение

Демонстрация REQ-INST-001 на чистой виртуальной машине Ubuntu 24.04. Тест REQ-AVAIL-002: `docker kill` контейнера API и проверка `/healthz` через минуту. Демонстрация REQ-AVAIL-003: восстановление из копии на чистой машине.

## Плюсы и минусы вариантов

### Compose + Caddy

* Хорошо, потому что минимум конфигурации и автоматический TLS.

### Compose + nginx + certbot

* Нейтрально, потому что привычная связка.
* Плохо, потому что два компонента и скрипт продления сертификата.

### Kubernetes (k3s)

* Хорошо, потому что масштабирование и самовосстановление.
* Плохо, потому что для одного сервера и четырёх контейнеров избыточно, а развернуть одной командой преподавателю сложнее.

### systemd без контейнеров

* Плохо, потому что зависимость от версии ОС, ручная установка PostgreSQL и Go, нет воспроизводимости (REQ-BUILD-001).

## Дополнительная информация

Связанные требования: REQ-INST-001, REQ-SEC-002, REQ-AVAIL-001…003, REQ-DIST-001, REQ-PORT-001, REQ-COST-001, ограничение C-5. Элементы SDD: DV-014.
