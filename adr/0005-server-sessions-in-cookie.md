# Серверные сессии в cookie вместо JWT

## Контекст и постановка задачи

После входа браузер должен доказывать серверу, кто пользователь. SRS требует завершать все сессии при выходе и при сбросе пароля (REQ-FUNC-004, REQ-SEC-003), передавать идентификатор только в cookie с `HttpOnly`, `Secure`, `SameSite=Lax` и завершать сессию после 30 дней неактивности.

Какой механизм аутентификации использовать между SPA и API-сервером?

## Драйверы решения

* Мгновенный отзыв всех сессий пользователя при сбросе пароля.
* Защита от кражи токена через XSS (cookie `HttpOnly`).
* Защита от CSRF для изменяющих запросов (REQ-SEC-009).
* Один API-сервер и одна БД, горизонтального масштабирования в R1 нет.

## Рассмотренные варианты

* Непрозрачный идентификатор сессии в cookie, сессии хранятся в БД
* JWT в cookie с коротким сроком и refresh-токеном
* JWT в `localStorage`

## Итог решения

Выбранный вариант: «Непрозрачный идентификатор сессии в cookie, сессии в БД», потому что только он даёт мгновенный отзыв сессий без дополнительных списков отзыва и проще всего в реализации.

### Последствия

* Хорошо, потому что выход и сброс пароля сводятся к `DELETE FROM sessions`.
* Хорошо, потому что в БД хранится только SHA-256 от идентификатора, и утечка базы не даёт рабочих сессий.
* Плохо, потому что каждый запрос делает поиск сессии в БД. При 50 одновременных пользователях это доли миллисекунды по первичному ключу.
* Нейтрально, потому что для CSRF используется схема double submit: cookie `csrf` и заголовок `X-CSRF-Token`.

### Подтверждение

Автотест REQ-SEC-003: после выхода прежний `sid` получает 401. Автотест REQ-FUNC-004: после сброса пароля все ранее выданные `sid` недействительны. Инспекция атрибутов cookie в ответе `/auth/login`.

## Плюсы и минусы вариантов

### Сессия в БД

* Хорошо, потому что мгновенный отзыв и простая модель.
* Нейтрально, потому что требует обращения к БД на каждый запрос.

### JWT в cookie + refresh

* Хорошо, потому что сервер не хранит состояние для каждого запроса.
* Плохо, потому что отзыв требует списка отзыва или ожидания истечения access-токена.
* Плохо, потому что две сущности токенов усложняют реализацию.

### JWT в localStorage

* Плохо, потому что токен доступен JavaScript и крадётся при XSS. Противоречит REQ-SEC-003.

## Дополнительная информация

Связанные требования: REQ-FUNC-003, REQ-FUNC-004, REQ-SEC-003, REQ-SEC-005, REQ-SEC-009. Элементы SDD: DV-004, DV-005, DV-008. При появлении входа через Steam OpenID в R2 решение остаётся в силе: OpenID только подтверждает личность, после чего создаётся такая же сессия.
