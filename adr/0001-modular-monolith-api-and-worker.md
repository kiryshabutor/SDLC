# Модульный монолит на Go из двух процессов: API-сервер и фоновый обработчик

## Контекст и постановка задачи

Система выполняет две разные по характеру работы. Первая — быстрые ответы пользователю (вишлист, страница игры, вход). Вторая — долгий фоновый цикл опроса Steam, который идёт до часа (REQ-PERF-004), и отправка писем. Разрабатывает систему один человек за шесть недель, а Заказчик требует Go (C-2).

Как разбить серверную часть на развёртываемые единицы, чтобы фоновая работа не мешала ответам пользователю и при этом не усложнять разработку?

## Драйверы решения

* Срок R1 — шесть итераций по одной неделе, один разработчик.
* Цикл опроса не должен влиять на время ответа API (REQ-PERF-001, p95 ≤ 300 мс).
* Перезапуск одного процесса не должен останавливать другой (REQ-AVAIL-002).
* Бизнес-логика должна тестироваться без внешних API (REQ-MAINT-001, REQ-MAINT-003).
* Масштаб R1 — до 1000 пользователей (A-9).

## Рассмотренные варианты

* Один процесс: HTTP-сервер и планировщик в одном бинарнике
* Модульный монолит: одна кодовая база, два процесса (api, worker)
* Микросервисы: auth, wishlist, pricing, notify отдельными сервисами

## Итог решения

Выбранный вариант: «Модульный монолит: одна кодовая база, два процесса», потому что он изолирует фоновую работу от API, не требуя межсервисного взаимодействия, и укладывается в срок одного разработчика.

### Последствия

* Хорошо, потому что общий код `internal/domain` и `internal/app` используется обоими процессами без дублирования.
* Хорошо, потому что процессы общаются только через PostgreSQL (таблица `jobs`, `LISTEN/NOTIFY`), и задания не теряются при перезапуске.
* Хорошо, потому что из одного образа Docker запускаются оба процесса с разной командой.
* Плохо, потому что оба процесса зависят от одной схемы БД, и миграции должны быть совместимы с обеими версиями во время обновления.
* Нейтрально, потому что при росте нагрузки модуль pricing можно выделить в сервис без переписывания: границы уже заданы пакетами.

### Подтверждение

Линтер `depguard` в CI запрещает импорт `internal/source/steam`, `internal/source/itad` и `pkg/*` из `internal/app` и `internal/domain`. На код-ревью проверяется, что API-сервер не вызывает долгих операций синхронно.

## Плюсы и минусы вариантов

### Один процесс

* Хорошо, потому что проще всего развернуть и отладить.
* Плохо, потому что цикл опроса и отправка писем конкурируют с HTTP за ресурсы и пул соединений.
* Плохо, потому что падение планировщика роняет сайт.

### Модульный монолит, два процесса

* Хорошо, потому что изоляция отказов и нагрузки.
* Хорошо, потому что одна сборка, один репозиторий, общие тесты.
* Нейтрально, потому что нужен механизм заданий между процессами (решается таблицей в PostgreSQL).

### Микросервисы

* Хорошо, потому что независимое масштабирование.
* Плохо, потому что для 1000 пользователей это избыточно: сетевые контракты, распределённые транзакции, несколько баз.
* Плохо, потому что не укладывается в шесть недель одного разработчика.

## Дополнительная информация

Связанные требования: REQ-DIST-001, REQ-AVAIL-002, REQ-MAINT-001, REQ-REUSE-001. Элементы SDD: DV-002, DV-003. Решение пересматривается, если число пользователей превысит 10 000 или появится второй магазин с собственным циклом опроса.
