# PostgreSQL как единственное хранилище, включая очередь заданий

## Контекст и постановка задачи

Система хранит пользователей, вишлисты, текущие цены, историю цен за два года, уведомления и исходящие письма (SRS, Приложение Б). Кроме того, API-серверу нужно передавать задания фоновому обработчику (ручная проверка, импорт вишлиста), а два цикла опроса не должны идти одновременно (REQ-DIST-001).

Какое хранилище выбрать и нужен ли отдельный брокер сообщений для заданий?

## Драйверы решения

* Данные реляционные: пользователь → вишлист → игра → цены по регионам.
* Нужны транзакции: цена, запись истории и уведомление сохраняются вместе (REQ-REL-006).
* Нужна очередь заданий и взаимное исключение циклов.
* Минимум компонентов для развёртывания одной командой (REQ-INST-001) и стоимость 0 USD (REQ-COST-001).
* Лицензия, допускающая свободное использование (REQ-COMP-004).

## Рассмотренные варианты

* PostgreSQL для данных, заданий и блокировок
* PostgreSQL для данных и Redis для очереди и блокировок
* SQLite

## Итог решения

Выбранный вариант: «PostgreSQL для данных, заданий и блокировок», потому что он закрывает все три потребности одним компонентом: транзакции, очередь через `SELECT … FOR UPDATE SKIP LOCKED` и `LISTEN/NOTIFY`, взаимное исключение через `pg_advisory_lock`.

### Последствия

* Хорошо, потому что одно хранилище: одна резервная копия, один пул соединений, одна точка мониторинга.
* Хорошо, потому что задание ставится в той же транзакции, что и изменение данных, и не может потеряться.
* Плохо, потому что очередь на PostgreSQL рассчитана на малый поток заданий (до сотен в минуту). Для R1 этого достаточно.
* Нейтрально, потому что схема управляется миграциями goose (REQ-INST-003), что требует дисциплины при изменениях.

### Подтверждение

Интеграционные тесты запускаются против PostgreSQL 16 в контейнере (testcontainers-go). Тест REQ-DIST-001 запускает два обработчика и проверяет, что `poll_cycles` не пересекаются по времени.

## Плюсы и минусы вариантов

### PostgreSQL для всего

* Хорошо, потому что транзакции, внешние ключи, `ON DELETE CASCADE` для удаления пользователя (REQ-FUNC-007).
* Хорошо, потому что оконные функции и индексы для истории цен и графиков.
* Нейтрально, потому что требует отдельного контейнера (в отличие от SQLite).

### PostgreSQL и Redis

* Хорошо, потому что Redis — привычный инструмент для очередей и ограничителей частоты.
* Плохо, потому что ещё один компонент, который надо разворачивать, резервировать и мониторить.
* Плохо, потому что задание и данные оказываются в разных хранилищах без общей транзакции.

### SQLite

* Хорошо, потому что встраивается в процесс, нулевая настройка.
* Плохо, потому что два процесса (ADR-0001) пишут в одну базу, а SQLite допускает только одного писателя одновременно.
* Плохо, потому что нет `LISTEN/NOTIFY` и advisory locks.

## Дополнительная информация

Связанные требования: REQ-FUNC-018, REQ-REL-006, REQ-DIST-001, REQ-INST-003, REQ-AVAIL-003, REQ-PERF-006, ограничение C-4. Элементы SDD: DV-004, DV-012, DV-015.
