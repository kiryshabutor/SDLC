# Telegram-бот на long polling, отправка через общий outbox

## Контекст и постановка задачи

Во втором раунде обсуждения плана (PR #2) Заказчик добавил в R1 уведомления в Telegram (REQ-FUNC-031): письма читают с опозданием, а Telegram просматривают сразу. Нужно привязать аккаунт Telegram к пользователю и доставлять уведомления так же надёжно, как письма (REQ-REL-005), не нарушая лимит Telegram 30 сообщений в секунду (REQ-INT-012). Сервер один и развёрнут через Docker Compose (ADR-0008), постоянного публичного адреса в тестовом окружении может не быть.

Как получать сообщения боту и как отправлять уведомления в Telegram?

## Драйверы решения

* Минимальные изменения ядра: функция добавлена поздно и должна уложиться в 18 ч.
* Доставка не теряется при сбое Telegram API и при перезапуске процесса.
* Работа без публичного HTTPS-адреса (локальная демонстрация).
* Бесплатность (REQ-COST-001).

## Рассмотренные варианты

* Long polling (`getUpdates`) в фоновом обработчике + отправка через `email_outbox` с полем `channel`
* Webhook в API-сервере + отдельная очередь сообщений Telegram
* Сторонний сервис рассылок в мессенджеры

## Итог решения

Выбранный вариант: «Long polling + общий outbox», потому что он не требует публичного адреса, повторно использует готовый механизм повторов outbox (ADR-0007) и добавляется новой реализацией интерфейса `Notifier` без изменения цикла опроса и проверки условий.

### Последствия

* Хорошо, потому что ядро (DV-007, DV-010) не меняется: дайджест цикла просто создаёт ещё одну запись outbox с `channel = telegram`.
* Хорошо, потому что демонстрация работает на компьютере разработчика без настройки вебхука.
* Плохо, потому что обработчик держит постоянное соединение `getUpdates`, и при двух экземплярах обработчика бот получал бы сообщения дважды. Это исключено: обработчик запускается в одном экземпляре (ADR-0006).
* Нейтрально, потому что название таблицы `email_outbox` перестаёт точно отражать содержимое; переименование отложено, чтобы не трогать готовые миграции.

### Подтверждение

Тест REQ-FUNC-031: после привязки по коду и срабатывания условий по 3 играм приходит одно сообщение; после `/stop` сообщения не отправляются. Тест REQ-INT-012: при имитации ответа 429 повтор не раньше `retry_after`.

## Плюсы и минусы вариантов

### Long polling + общий outbox

* Хорошо, потому что просто и надёжно.
* Плохо, потому что задержка приёма кода привязки до 30 с (таймаут long polling). Для привязки это несущественно.

### Webhook + отдельная очередь

* Хорошо, потому что мгновенный приём сообщений и стандартный подход для production.
* Плохо, потому что нужен публичный HTTPS-адрес и отдельная очередь с собственными повторами: ещё около 6 ч работы.

### Сторонний сервис рассылок

* Хорошо, потому что не нужно писать бота.
* Плохо, потому что платные тарифы и передача chat_id пользователей третьей стороне (REQ-COMP-001).

## Дополнительная информация

Связанные требования: REQ-FUNC-006-2, REQ-FUNC-031, REQ-INT-012, REQ-REL-005, REQ-COST-001. Элементы SDD: DV-002, DV-004, DV-005, DV-013. Функция плана: F-22.
